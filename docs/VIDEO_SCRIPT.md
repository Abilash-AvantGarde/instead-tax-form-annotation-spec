| 0:00-0:30 | File tree, root of `instead-submission/` | "The brief was to design a spec for annotating boxes on a U.S. tax form, so someone else's code can print values into them using my format. I went with JSON Schema. Why JSON over XML or custom classes: it's directly validatable, every popular language parses it with zero extra library weight, and it's readable by a non-engineer who just needs to add a new field — which matters, because the person annotating a form and the person building the renderer are different people with different skills." |
| 0:30-1:15 | `spec/annotation.schema.json`, scrolled to the top-level `properties` and `$defs.field` | "The schema has one entry point — an array of fields. Every field shares one definition, `$defs.field`, so a date field and a checkbox field go through the identical checklist: an id, a label, a box, a type. Then it branches based on that type — a currency field requires a `value` binding, a table requires `axis`, `itemsPath`, and `pitch`, a radio group requires `options`. One shape, a few type-gated branches, `additionalProperties: false` everywhere so nothing undocumented sneaks in." |
| 1:15-2:45 | `spec/f1040.annotation.json`, scrolled to `f1040.line1a`; then `data/sample-taxpayer.json`, `income.w2`; then the rendered PDF output | "Concrete example: line 1a, total W-2 wages. `box` says page 1, exact x and y in PDF points, top-left origin. `type` is currency. `value.path` is `$.income.w2[*].box1Wages` — that wildcard means 'every W-2 in the data,' and because it's a wildcard it requires an `aggregate`, here `sum`. `format` says zero decimal places, round half-up, negative amounts in parentheses — the actual IRS convention. In the sample data there are two W-2s, 86,250 and 54,121.08. The renderer resolves the path, sums both, formats to 140,371, and draws it at that exact box." Switch to terminal, run the prebuilt jar: `java -jar renderer/target/annotation-renderer.jar --annotation spec/f1040.annotation.json --data data/sample-taxpayer.json --pdf forms/f1040.pdf --out output/f1040-filled.pdf`. Open the output PDF. "That's position, formatting, and a nested-data reference, in one five-line field definition — repeated 76 times for the full two-page 1040, and 38 more times for a completely separate form, the W-2." |
| 2:45-3:30 | `renderer-python/render.py` and `renderer-node/render.js` side by side; then the dependents table in `spec/f1040.annotation.json` | "Two things I think stand out. First: I built three independent renderers — Java, Python, Node — zero shared code, and all three read the exact same annotation file and produce identical output. That's the actual proof this spec is portable, not just something that happens to work with one renderer. Second: the 1040's dependents section doesn't repeat down the page like a normal table — it repeats sideways, four slots side by side. My table type has an explicit `axis: columns` with a `pitch` offset, so it describes that correctly instead of forcing a row-based shape onto data that isn't row-shaped." |
| 3:30-4:15 | `docs/SPEC.md`, the non-goals / design-decisions section | "Three decisions I'd defend. PDF points with top-left origin, because every coordinate tool reports that directly — I only do one documented flip at draw time. A restricted path syntax — no filters, no functions, just dot access and wildcards — so the annotation file stays inert data that anyone can audit just by reading it. And the one I'd argue hardest for: the annotation can never do cross-line tax arithmetic. Line 9 is a sum of other lines; I deliberately gave it no way to express that. The moment a field can reference another field, it's a tax engine, not a presentation layer, and tax engines need a test suite, not a data file a non-engineer edits by hand." |
| 4:15-4:50 | `docs/SPEC.md` future enhancements section | "Next steps that build directly on this design: nested repeats, like each W-2 having its own repeating box-12 codes — the planner already passes a per-instance data scope down the recursion for the dependents table, so that's an extension, not a rewrite. Conditional fields that only print when another value matches. And treating disagreement between two independently built renderers as an automated signal that the spec's wording is ambiguous, not that one renderer is wrong — a cheap, continuous way to pressure-test the spec as it grows." |
| 4:50-5:00 | Repo root again | "Schema, two real forms, three renderers that agree, and a table type that handles data that doesn't repeat in a straight line. Thanks for watching." |
